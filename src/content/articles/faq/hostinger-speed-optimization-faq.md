## 先说结论

> **一句话结论**：网站慢的原因按影响排序，是**图片体积 → 外部请求 → 后端响应（TTFB）→ 前端渲染**；90% 的"主机太慢"其实是前两项造成的，在被引导去升级套餐之前，先花二十分钟测一遍数据 —— 你可能会发现问题根本不在主机上。

- **适合谁**：站点能跑但觉得慢的用户；已经试过装缓存插件但没效果的人；被 PageSpeed 分数吓到但不知道怎么动手的人
- **不适合谁**：站点直接打不开、报 500 错误的用户。那是故障排查问题（见文末），不是性能优化问题 —— 先让它能打开，再谈快不快
- **我们的立场**：按"影响从大到小"排序，把优化项做成可勾选的清单。所有命令都可以直接复制执行，不做"建议联系服务商"这种无效建议

## 第 0 步：先测基线，别急着改

这一步最容易被跳过，但它决定了后面所有工作的效率。**在动手之前，记录三个数字：**

| 指标 | 怎么测 | 健康区间 |
| --- | --- | --- |
| TTFB（首字节时间） | 浏览器 F12 → Network → 看第一个文档请求的 Waiting 值 | 共享主机 200–500ms |
| LCP（最大内容绘制） | PageSpeed Insights 或 Lighthouse 的 Largest Contentful Paint | < 2.5s |
| 页面总重量 | F12 → Network → 底部看到的 transferred 总和 | < 1.5MB |

**测之前务必做的两件事**：

1. **用无痕窗口测**，避免浏览器缓存干扰结果
2. **关掉本地代理**。如果你挂着代理去测一个部署在海外的站点，测出来的是代理的速度不是主机的速度 —— 这个错误会让很多人误判主机性能

**为什么要基线**：优化完之后你会分不清"是这次改动生效了"还是"今天网络好"。有基线才有对比。

## 一、图片与静态资源（收益最大，先做这里）

### Q1. 为什么说图片是最大的问题？

一个未压缩的 4000px 宽拍摄原图可能有 4–6MB，而它显示在页面上只需要 800px 宽。**你让访客下载了 6 倍于必要的数据。** 一个页面放 5 张这样的图，就是 25MB —— 在 4G 网络上打开需要十几秒。

**修法**：
```bash
# macOS 下批量转 WebP 并缩放到 1600px 宽
for f in *.jpg; do
  cwebp -q 82 -resize 1600 0 "$f" -o "${f%.jpg}.webp"
done
```
如果不想装工具，用 [Squoosh](https://squoosh.app) 这类在线工具，或者 WordPress 里装 ShortPixel / Imagify 插件自动处理。

**判断标准**：单张图片控制在 **150KB 以内**，WebP 格式，缩放后尺寸不超过实际显示宽度的两倍。

### Q2. 懒加载是不是装上就一定好？

**不是，首屏图片绝对不能懒加载。**

懒加载的原理是"图片进入视口才加载"。如果你把首屏那张大图也设成懒加载，浏览器要等 JS 执行完、计算完视口位置，才开始下载这张图 —— **LCP 会反而变慢**。

**正确的做法**：
```html
<!-- 首屏英雄图：正常加载，加 fetchpriority -->
<img src="hero.webp" fetchpriority="high" width="1200" height="600" alt="...">

<!-- 首屏之外的图：懒加载 -->
<img src="below.webp" loading="lazy" width="800" height="450" alt="...">
```

WordPress 从 5.5 起默认开启图片懒加载，**你需要手动把它从首屏图片上排除**（多数主题有选项，或加 `skip-lazy` class）。

### Q3. 图片尺寸的宽高属性真的重要吗？

**非常重要，这是最便宜的一项改进。**

没写 `width` / `height` 时，浏览器不知道图片占多大位置，只能先按 0 高度排版，等图片下载完再重排整个页面 —— 这就是 **CLS（累积布局偏移）**。用户正在读的内容会突然跳走。

加上宽高属性后，浏览器能提前预留空间。**这是一行 HTML 的事，收益立竿见影。**

### Q4. 字体文件也要压缩吗？

要。中文字体尤其坑 —— 一个完整的中文字体文件（如思源黑体）动辄 5–10MB，因为包含数千个字形。

**三个解法**：

1. **用系统字体栈**，不加载任何 Web 字体。最快，也最稳：
```css
font-family: -apple-system, BlinkMacSystemFont, "Segoe UI", 
             "PingFang SC", "Microsoft YaHei", sans-serif;
```
2. **字体子集化**：只打包页面上实际用到的字（`fonttools` 或 Fontmin 可以做），中文字体能从 8MB 压到 100KB 以内
3. **`font-display: swap`**：让文字先用系统字体渲染，字体加载完再替换，避免"文字隐形"阶段

## 二、外部请求与前端资源（第二大头）

### Q5. 第三方脚本到底有多伤性能？

**一个访客统计脚本、一个在线客服插件、一个社交分享按钮，加起来能让 LCP 增加 1–2 秒。** 因为它们通常不在你的服务器上，且经常阻塞渲染。

**排查方法**：F12 → Network → 按 Size 排序，看哪些请求来自别人的域名。

**典型元凶**：
- Google Fonts（尤其是没做子集化的中文字体，单个 CSS 请求可能引出 10MB 字体）
- 多个统计/热图脚本叠加（GA + 百度统计 + Clarity + Hotjar）
- 在线客服插件（多数会注入 200KB+ 的 JS）
- 未加 `debounce` 的滚动监听脚本

**处理原则**：**能不装就不装。** 每个第三方脚本都在向你的访客收"加载税"。只保留真正在看的那个统计工具。

### Q6. 怎么在不删功能的前提下减轻影响？

如果某个脚本必须留（比如客服），按这个顺序处理：

1. **加 `defer` 或 `async`**，让它不阻塞 HTML 解析
2. **延迟到用户交互后再加载** —— 用户滚动或移动鼠标时才注入脚本
3. **本地托管**：把字体、库文件下载到自己服务器，省掉 DNS 查询和跨域握手

```html
<!-- 延迟加载：用户首次交互后才注入客服脚本 -->
<script>
  const loadChat = () => {
    const s = document.createElement('script');
    s.src = '/assets/chat-widget.js';
    document.body.appendChild(s);
    window.removeEventListener('scroll', loadChat);
    window.removeEventListener('mousemove', loadChat);
  };
  window.addEventListener('scroll', loadChat, { once: true, passive: true });
  window.addEventListener('mousemove', loadChat, { once: true, passive: true });
</script>
```

### Q7. CSS 和 JS 要不要合并？

**HTTP/2 时代，合并的收益已经很小，甚至可能有害。**

每个请求都有开销，但 HTTP/2 支持多路复用，多个小文件的请求开销远低于 HTTP/1.1 时代。而把所有 CSS 合成一个文件，意味着**用户为了看首屏也要下载整个站点的样式**。

**现代做法**：
- 关键 CSS（首屏渲染必需的）内联到 `<head>`
- 其余 CSS 异步加载
- JS 按路由/组件拆分，用 `defer` 加载

如果用的是 Astro / Next.js 这类框架，**这些它已经帮你做了，不要手动再合一遍**。

## 三、后端响应与 TTFB（真正和主机相关的部分）

### Q8. TTFB 高说明什么？

TTFB 是从发出请求到收到第一个字节的时间，**它衡量的是"服务器思考的时间"**。

- **200–400ms**：健康
- **400–800ms**：有优化空间，先查插件与查询
- **> 800ms**：后端确实在花时间，需要定位到具体原因

**注意**：TTFB 也包含网络传输时间。如果你在亚洲测一个美国机房的主机，光往返就可能 200ms+ —— 这部分不是"主机慢"，是物理距离。

### Q9. 怎么定位 TTFB 到底慢在哪里？

用一个请求测三次，对比结果：

```bash
# 安装
npm i -g autocannon

# 或者直接用 curl 看各阶段耗时
curl -w "dns: %{time_namelookup}s\nconnect: %{time_connect}s\nttfb: %{time_starttransfer}s\ntotal: %{time_total}s\n" \
  -o /dev/null -s https://你的域名.com/

# 测三次取平均，排除偶发抖动
for i in 1 2 3; do
  curl -w "%{time_starttransfer}\n" -o /dev/null -s https://你的域名.com/
done
```

**读法**：
- `time_namelookup` 高 → DNS 解析慢，考虑换 DNS 服务商
- `time_connect` − `time_namelookup` 高 → 网络延迟大，是物理距离问题
- `time_starttransfer` − `time_connect` 高 → **这才是服务器处理时间**，也是你能优化的部分

### Q10. 服务器处理时间高的常见原因有哪些？

按出现频率排：

1. **无缓存的 WordPress 首页**。每一次访问都在重新查询数据库、重新渲染模板
2. **未优化的数据库查询**。`WP_Query` 用了 `meta_query` 却没有索引
3. **插件过多**。一个典型 WordPress 站装 25 个插件，每次请求要加载 25 份代码
4. **外部 API 调用**。主题在服务端等着调用某个第三方接口，接口慢 = 你的站慢
5. **PHP 版本过旧**。PHP 8.x 比 PHP 7.4 有 20%–40% 的性能提升

### Q11. PHP 版本怎么改？

在 hPanel 里：**高级 → PHP 配置**，选择 8.2 或 8.3。

**注意**：改完必须完整点一遍网站。有些老插件/老主题在 PHP 8 下会报 deprecated 警告甚至致命错误。**改版本前先备份，改完之后立刻测。**

如果站点报错，先切回原版本，再逐个排查插件兼容性 —— hPanel 的 PHP 错误日志会直接告诉你哪个文件、哪一行出问题。

## 四、缓存策略（免掉重复计算）

### Q12. 缓存到底缓存了什么？

**页面缓存**：把渲染好的 HTML 存成文件，下次访问直接返回，跳过 PHP 和数据库。这是收益最大的一层。

**对象缓存**：把数据库查询结果存进内存（Redis / Memcached），适合有登录用户、不能用全页缓存的站点。

**浏览器缓存**：告诉访客的浏览器"这个文件 30 天内不用再问我"。由响应头控制。

**三层是叠加的，不是二选一。**

### Q13. 共享主机上缓存插件怎么选？

| 插件 | 适合场景 | 注意 |
| --- | --- | --- |
| LiteSpeed Cache | Hostinger 用的就是 LiteSpeed 服务器 —— **首选** | 与服务器深度集成，能用到 LSCache |
| WP Super Cache | 只想要简单的全页缓存 | 配置项少，上手快 |
| W3 Total Cache | 需要细粒度控制 | 配置复杂，配错反而变慢 |
| WP Rocket | 付费，但开箱即用 | 预算允许时最省心 |

**Hostinger 用户直接用 LiteSpeed Cache。** 它和服务器是同一套技术栈，能用到普通插件用不到的服务器级缓存。

**关键配置**（LiteSpeed Cache 里）：
- 开启 **Page Cache**
- 开启 **Browser Cache**（设置静态资源过期时间）
- 图片优化里开启 **WebP 替换**
- **不要**在共享主机上开 Object Cache（没有 Redis 时会退化成本地盘，收益为负）

### Q14. 缓存插件装了还是慢，为什么？

因为**缓存能免掉重复计算，但不能免掉必须算的那一次**。三个常见原因：

1. **缓存没有命中**。看响应头里的 `X-LiteSpeed-Cache: hit` 还是 `miss`。如果是 `miss`，说明有东西在绕过缓存 —— 通常是某个插件在每次请求时设置 cookie（很多统计、多语言、会员插件会这么做）
2. **没登录状态正常、登录后慢**。缓存默认对已登录用户不生效，这是设计如此
3. **瓶颈不在后端**。如果 TTFB 已经很低（< 300ms）但页面还是慢，问题在前端，回到第一节和第二节

## 五、数据库与插件（WordPress 站的隐性成本）

### Q15. 数据库怎么会拖慢速度？

WordPress 的 `wp_options` 表里有一个 `autoload` 字段。**任何标记为 autoload = yes 的选项，都会在每一次页面请求时被全部加载。** 插件卸载不干净时会留下大量孤儿数据。

**检查方法**（在 phpMyAdmin 里执行）：
```sql
-- 看 autoload 数据总量
SELECT SUM(LENGTH(option_value)) AS autoload_size, COUNT(*) AS autoload_count
FROM wp_options WHERE autoload = 'yes';
```

**判断标准**：
- `autoload_size` **小于 800KB** 正常
- **800KB–2MB** 需要清理
- **超过 2MB** 会明显拖慢每一个请求 —— 这是很多"查不出原因的慢"的真相

**清理**：先备份数据库，然后用 WP-Optimize 或 WP-Sweep 清理孤儿选项与修订版本。**不要手动 DELETE，也不要清理你不认识的行** —— `wp_options` 里的东西删错了站点会直接白屏。

### Q16. 文章修订版本会占多少空间？

**每保存一次草稿就存一个完整副本。** 写一篇长文改 30 次，就是 30 份副本。半年下来几百 MB 很常见。

在 `wp-config.php` 里限制：
```php
define('WP_POST_REVISIONS', 5); // 每篇最多保留 5 个修订版本
```
**注意**：加这行之前先备份。已有的历史修订不会自动删除，需要用 WP-Optimize 单独清理。

### Q17. 插件数量有上限吗？

没有硬性上限，但有**成本曲线**。真正的问题不是数量，是：

- 每个插件都在 `init` 钩子上跑代码
- 有些插件在前台加载了自己用不到的 JS/CSS（这是最常见的浪费）
- 插件之间会互相冲突，产生重复查询

**判断方法**：用 Query Monitor 插件看每次请求的查询数、慢查询、以及每个插件占用的时间。**如果一个插件的耗时超过 100ms 且功能可以被替代，就该考虑换掉它。**

## 六、CDN 与网络层

### Q18. 免费 Cloudflare 值得开吗？

**取决于你的访客在哪。**

| 访客位置 | 免费 Cloudflare 的效果 |
| --- | --- |
| 北美 / 欧洲 | ✅ 提升明显，静态资源命中边缘节点 |
| 东南亚 / 日韩 | ✅ 有一定提升 |
| **中国大陆** | ⚠️ 节点在境外，可能反而变慢，且存在访问稳定性问题 |

**如果你的用户主要在中国大陆**，用 Hostinger Business 套餐自带的 CDN（企业级 Cloudflare，但有优化的路由），或者接受"直接把服务器放在离用户近的地方"这个更朴素的方案。

### Q19. Brotli 和 HTTP/3 要手动开吗？

**不用，多数情况已默认开启。** 你可以在 F12 → Network → 响应头里确认：

- `content-encoding: br` → Brotli 已生效
- `alt-svc: h3=":443"` → HTTP/3 可用

这两项加起来大约 5%–15% 的提升，属于"顺手确认一下"的项。**但它们救不了一个本来就重 5MB 的页面** —— 别把顺序搞反。

## 七、什么时候该换主机

### Q20. 怎么判断瓶颈真的在主机？

**同时满足这三个条件时，才考虑升级或迁移：**

- [ ] **hPanel 的 CPU / 内存曲线长期接近 100%**（不是偶尔尖峰，是持续高位）
- [ ] **已经完成前四类优化**：图片压缩、第三方脚本清理、缓存开启并命中、数据库 autoload 清理
- [ ] **TTFB 稳定超过 800ms**，且换一个网络环境复测仍然如此

三个条件都满足，说明你已经把软件层能做的都做完了，剩下的确实是资源配额不够。

**这时候的选择**：

| 现状 | 建议 |
| --- | --- |
| 共享主机（Single/Premium/Business）撞限 | → Business（若还在低档）或 Cloud Startup |
| 共享主机顶配仍撞限 | → Cloud Startup（资源隔离 + 自动扩容） |
| 需要 root 权限、愿意自己运维 | → KVM 2 或 KVM 4 VPS |
| 只是偶尔有流量尖峰 | → 先别升级，用缓存扛过去 |

**反过来说**：如果 TTFB 只有 300ms 但 PageSpeed 分数很低，你的主机没问题，**问题在前端**。这时候升级套餐是纯粹的浪费钱 —— 新主机一样会渲染同样重的前端。

## 快速自查清单

拿去照着做，按顺序，做完一项打个勾：

- [ ] **测基线**：TTFB、LCP、页面总重量（无痕窗口，关代理）
- [ ] **图片**：全部转 WebP，单张 < 150KB，补上 width/height
- [ ] **首屏图**：排除懒加载，加 `fetchpriority="high"`
- [ ] **字体**：改用系统字体栈，或做子集化 + `font-display: swap`
- [ ] **第三方脚本**：F12 按域名排序，删掉不用的，剩下的加 defer
- [ ] **PHP 版本**：升到 8.2 或 8.3，升级后完整点一遍站
- [ ] **缓存插件**：装 LiteSpeed Cache，确认响应头显示 `hit`
- [ ] **数据库**：查 autoload 总量，超 2MB 就清理
- [ ] **插件审计**：用 Query Monitor 找出耗时 > 100ms 的插件
- [ ] **CDN**：按访客所在地决定要不要开
- [ ] **复测**：用同样的方法再测一遍，和基线对比
